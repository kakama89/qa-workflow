# Excel template handling

## General policy

Every person or team may use a different template. Treat the template as a
starting point, not a fixed schema, and never assume sheet names, row
numbers, column order, formula ranges, or dropdown ranges. Detect them with
`validate_workbook.py profile` each time.

Template changes are allowed but every material change must be proposed in
Step 4 and approved before export. The original template is never modified;
output always goes to a new file.

## Choosing the template

1. The tester's saved profile (`qa_profiles.py list`), when one exists.
2. The tester's own template file, when provided; offer to save it as a
   profile.
3. Otherwise the bundled default `assets/template.xlsx`.

## Tester profiles

`scripts/qa_profiles.py` saves a profile as
`<home>/profiles/<name>.json` plus a template copy in `<home>/templates/`,
where `<home>` is `%USERPROFILE%\.kiro\qa-workflow` (personal) or `<project>\.kiro\qa-workflow`
(shared). Example profile:

```json
{
  "name": "ngan-api",
  "owner": "ngannt23",
  "template": "templates/ngan-api.xlsx",
  "layout": {"sheet": "Testcases", "header_row": 12, "data_start_row": 14,
             "col": ["id=A", "title=B", "precondition=C", "steps=D", "expected=F"]},
  "required": "id,steps,expected",
  "metadata": {"Originator:": "ngannt23", "Cover!E14": "Tester"}
}
```

`--profile NAME` on `validate_workbook.py` and `export_workbook.py` loads the
template, layout, required fields, and metadata; options given on the command
line override the profile. `--profile default` uses the default profile.

Metadata keys are either label text (the value is written into the first cell
right of the label, after any merged label cells; the first match wins) or an
exact cell such as `Cover!E13`. Values in the cases JSON `metadata` override
profile metadata.

## How layout detection works

`validate_workbook.py` and `export_workbook.py` share the same detection:

- **Test Case sheet and header row**: the row (within the first 60 rows) with
  at least 3 known headers, including Test Steps or Expected Result. English
  and Vietnamese aliases are recognized, for example `Test case Id` / `Mã test
  case`, `Test Steps` / `Các bước thực hiện`, `Expected result` / `Kết quả
  mong muốn`.
- **Column roles**: `id`, `title`, `precondition`, `steps`, `data`,
  `expected`, `environment`, `priority`, `automation`, `result`, `bug`,
  `notes`, `requirement`, `ac`, `review`. Unrecognized headers are listed as
  "unmapped".
- **Guide rows**: instruction rows directly under the header (long text in
  the ID column) are skipped.
- **Test case row**: a row with Test Steps or Expected Result. A row with only
  a title is a section/group row.
- **ID convention**: literal IDs, or an ID formula filled down the column
  (for example `=IF(D15<>"","[FN_"&TEXT(...),"###")&"]","")`).
- **Merged cells** are read from their top-left cell.

If detection is wrong, override it with `--sheet`, `--header-row`,
`--data-start-row`, `--col ROLE=COLUMN` (column letter or exact header text).
Use the same overrides for profile, export and validate.

## Bundled default template (`assets/template.xlsx`)

- Sheets: `Cover`, `Records`, `Testcases`, `Test Report`.
- `Testcases`: header on row 12, instruction row 13, data from row 14.
  Columns A–L: `Test case Id`, `Test case Title`, `Pre-conditions`,
  `Test Steps`, `Test Datas`, `Expected result`, `Test Environment`,
  `Priority`, `Automation Status`, `Test Results`, `BugID`, `Notes`.
- IDs are generated by formula `[FN_###]` in column A for rows with Test
  Steps; section rows (title only) get no ID.
- Dropdowns on rows 14–1000: Environment `Dev/Test/UAT/Pre-Production/
  Production`, Priority `High/Medium/Low`, Automation `Yes/No`, Results
  `Passed/Failed/Accepted/N/A/Untested`.
- Summary counts in `Testcases!B5:B10` and `Test Report` rows 15–19.
- `Test Report!G18` ("Test coverage") = (Passed + Failed + N/A) / Total and
  `G19` ("Test successful coverage") = (Passed + N/A) / Total. These keep the
  original team definitions; confirm them with the user (see *Report
  metrics*) and propose changes in the Template Change Review if needed.

## Cases JSON for `export_workbook.py`

```json
{
  "metadata": {"Project Name:": "<project>", "Created Date:": "2026-10-29", "Version:": "1.0"},
  "cases": [
    {"section": "Đăng nhập"},
    {
      "id": "",
      "title": "Đăng nhập thành công",
      "precondition": "Tài khoản ở trạng thái Active",
      "steps": "1. Nhập username <USERNAME>\n2. Nhập password <PASSWORD>\n3. Bấm Đăng nhập",
      "data": "",
      "expected": "3.1 Hiển thị trang chủ",
      "priority": "High",
      "columns": {"Notes": "Assumption — review required (ISSUE-02)"}
    }
  ]
}
```

- Keys are column roles. Use `columns` for template headers without a role.
- Leave `id` empty to use the template's ID formula; give literal IDs for
  templates without one.
- The script refuses to write (nothing is saved) when a key has no matching
  column, an ID is duplicated, a result value is an execution result during
  design, or a value looks like a credential.
- Existing rows in the template: default is to refuse; `--existing clear`
  replaces them and `--existing append` writes after them. Pick the option
  approved in Step 4.
- The script extends dropdowns, summary formula ranges, and filters to the
  last written row, copies row styles, and lists what it changed. Conditional
  formatting that stops early is reported, not changed.

## Recommended improvements to propose when relevant

- Add `Requirement ID` and `Acceptance Criteria ID` columns, or a separate
  traceability sheet.
- Add a `Requirement Issues` sheet if the team needs a record of unresolved
  ambiguities and decisions.
- Standardize dropdown values for environment, priority, automation status,
  test result, and review status.
- Define Test Report metrics and denominators clearly.
- Separate test design status from execution status.
- Populate Cover/Records metadata only when known; never copy old
  author/reviewer/project values as if current.
- Remove broken defined names (`#REF!`) and unrelated sheets only with
  approval.

## Report metrics

"Coverage" is not one universal metric. Define separately when needed:

- Requirement coverage = requirements with at least one linked test /
  in-scope testable requirements.
- AC coverage = ACs with at least one linked test / in-scope testable ACs.
- Execution progress = executed cases / cases in scope.
- Pass rate = passed cases / executed cases eligible for pass/fail.
- Defect count = defects linked to failed cases, per the team's tracking
  rules.

State how `Untested`, `Accepted`, `N/A`, blocked, and excluded cases are
treated. Never count unexecuted cases as passed.

## Workbook implementation notes

- Prefer `scripts/export_workbook.py`; for other edits use `openpyxl` on the
  output copy.
- openpyxl does not recalculate formulas. Formula-generated IDs and totals
  show their values only after the file is opened in Excel or LibreOffice;
  say so in the handoff.
- Macro-enabled templates (`.xlsm`) must be written as `.xlsm`. Legacy `.xls`
  must be saved as `.xlsx` first.
- Do not remove hidden sheets, named ranges, external links, formulas, or
  validation rules without checking their purpose.
- Never print secret values in chat or logs; report the cell location only.
